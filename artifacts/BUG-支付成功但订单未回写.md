# BUG：支付网关已确认收款，但订单状态没回写（付了钱、订单不可用）

- **严重级别**：高（用户真金已扣、订单却不可用 —— 看不到票、也退不了款）
- **发现时间**：2026-09-29
- **涉及环境**：**生产 + 测试都出现**（两类表现，同一根因方向）
- **复现样本**：生产 61008472、生产 61008632（对照）、测试 72890316

## 一、现象 A（生产 61008472）：订单**一直停在待付款**

| 探针 | 返回 | 含义 |
|---|---|---|
| `GET /v1/unifiedPay/paySuccess?subjectId=61008472` | `{"success": true}` | 支付侧确认收款 |
| `GET /v1/miguPay/paySuccess?subjectId=61008472` | `{"success": true}` | 同上（另一套支付系统） |
| `GET /v1/order/61008472` | `status=1(待付款)` | **订单侧不认账** |
| `GET /v1/shopTrade/refund/refundable/61008472` | `500 订单不存在或未支付` | 连退款都拿不到这笔单 |

补单接口 `POST /v1/miguPay/test/forceSyncAll` 返回：

```
全量同步: 补单0 等待1 失败10
```

→ **补不回来**。订单至今停在待付款。

## 二、现象 B（测试 72890316）：订单被**超时关闭**

测试环境收银台窗口只有 **118 秒**（生产 899 秒）。实测时间线：

| 时刻 | 观测 |
|---|---|
| T+0s | 下单，`status=1(待付款)`，窗口 118s |
| T+79s | `status=1`、`paySuccess=false`（付款尚未落库） |
| T+118s | 订单超时 → `status=4(已关闭)` |
| T+~180s | `paySuccess=true`、`payDetail` 返回 `23002 订单已支付` —— **钱到了，订单已关** |

结果：**钱扣了，订单是"已关闭"**，既不能用也退不了。
诱因像是"支付结果回写 > 订单超时关闭"的竞态，但**回写为何会慢到超过 2 分钟**需要开发查。

## 三、对照实验（证明 `paySuccess=true` 不是假阳性）

担心 `paySuccess` 对任何订单都返回 true，做了对照：

| 样本 | `paySuccess` 返回 |
|---|---|
| 从未支付的订单（如被核销过的 0 元单 72890348/72890279…） | `400 不存在的支付凭证：4\|72890348` |
| **新建订单 + 建支付凭证 + 不付款**（61008632 对照单） | `{"success": false}` |
| **真的付过款的订单**（61008472 / 72890316 / 72890421） | `{"success": true}` |

→ `true` **确实是"支付侧收到钱"**，不是误报。所以上面两例都是**钱真的扣了**。

## 四、影响与建议

1. **用户视角**：付款成功 → 订单不存在/已关闭 → 看不到票，且无法自助退款（退款入口要求"订单已支付"）。
2. 建议排查：
   - 支付回调（notify）与主动查单（`MiguPayResultQueryJob`）哪一环丢了；
   - **订单超时关闭任务与支付结果回写的竞态**：测试环境窗口只有 118 秒，更容易撞；
   - 订单关闭后若发现该单已收款，是否有**补偿落单**逻辑（目前 `forceSyncAll` 补不回来）。
3. 回归套件已适配：测试环境**不再依赖真人付款**跑部分退（改用 0 元夹具单，
   下单即已支付、无资金流动），避免继续踩这个"付款窗口期"的坑。

## 五、成本记录
