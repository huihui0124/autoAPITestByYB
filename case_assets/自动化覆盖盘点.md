# 自动化覆盖盘点

更新时间：2026-09-30

本文档用于把当前仓库里的自动化测试资产梳理成“上线回归地图”。它不是测试报告，而是后续对齐 2000+ 人工用例、设计 `release_core` 回归包、补齐自动化缺口的底稿。

配套的机器可读映射表见：`用例自动化映射.csv`。

## 2. Marker 现状

| Marker | 当前定位 | 典型入口 | 风险/依赖 |
|---|---|---|---|
| `smoke` | 环境可达、C 端登录态 | `./run.sh smoke` | 需要 C 端登录态；店铺接口免登录 |
| `catalog` | 清单结构、白名单、派生配置 | `./run.sh catalog check` / `pytest -m catalog` | 纯本地，不打环境 |
| `chain` | 商品、下单、支付记录、未支付探针 | `./run.sh chain` | 会创建订单；生产需写闸门 |
| `b_verify` | 出票后 B 端核销、重复核销、多次核销 | `./run.sh b` | 需要 B 端会话；会核销票 |
| `refund` | B 端退款、部分退 | `./run.sh refund` | 需要 B 端会话；会真退/改订单 |
| `real_pay` | 人工扫码真实支付闭环 | `./run.sh realpay` | 需要人工扫码；会产生资金流水 |
| `reg930` | 930 回归套件 | `./run.sh reg930` | 生产 888 店；含写操作；部分人工/半自动 |
| `demo` | 内存教学用例 | `pytest -m demo` | 不进入上线回归 |

## 4. 当前风险闸门

| 闸门 | 作用 | 位置 |
|---|---|---|
| `MIGU_CATALOG_ENFORCE` | 下单白名单，默认开启 | `migu_api/catalog.py` |
| `MIGU_ALLOW_PROD_WRITE` | 生产写操作默认拦截 | `migu_api/config.py`、`run.sh` |
| `MIGU_CI=1` | CI 跳过 `refund` / `real_pay`，禁止 `--real-pay=on` | `conftest.py` |
| `MIGU_REAL_PAY` / `--real-pay` | 控制真实支付/人工扫码 | `migu_api/fundgate.py` |
| `MIGU_ENV` / `MIGU_B_ENV` | C/B 环境独立切换 | `migu_api/config.py` |

这些闸门是后续建设 `release_core` 时必须保留的底线。

## 5. 初步覆盖结论

当前自动化已经覆盖了上线回归里最核心的几条主干：

- C 端登录与环境探针
- 商品清单与下单白名单
- 商品在售、下单、支付记录、未支付探针
- 真实支付到出票的受控闭环
- B 端单次核销、多次核销、重复核销拒绝
- B 端退款、部分退、退款三通路
- 非选座/选座/实名/电子票/身份证/快递/自取等关键组合
- 部分 B 端配置回读

但它还不是“全量上线回归体系”，主要缺口在：

1. 2000+ 人工用例尚未与自动化建立 `case_id -> pytest` 映射。
2. 缺少正式的 `release_core` marker，当前更多是按技术分组跑。
3. 短信、人机验证、复杂前端交互仍以人工或半自动为主。
4. 组合覆盖还依赖 930 套件，尚未沉淀成稳定的分层回归包。
5. B 端会话有效性目前部分用例只看缓存文件是否存在，前置探活还可以更早。
6. Allure 附件里可能包含订单号、支付入口、电子票码等敏感业务现场，CI 上传时需要治理。

## 6. 建议的第一版 release_core

第一版不要追求“全部自动化”，先把上线失败会直接影响买票、入场、退款的链路固定下来。

建议纳入 `release_core` 的自动化范围：

| 层级 | 建议纳入项 | 当前对应 |
|---|---|---|
| L0 冒烟 | 店铺、登录态、清单健康 | `smoke` + `catalog` |
| L1 下单支付前 | 商品在售、下单、支付记录、未支付探针、未开售拒单 | `chain` |
| L1 核销 | B 端订单可见、单次核销、重复核销拒绝、多次核销 | `b_verify` |
| L1 退款 | 可退性、试算、退款闭环、部分退闭环 | `refund` |
| L1 关键组合 | 非选座电子票、选座实名身份证、快递、自取 | `reg930` 中 TC-005~TC-008 |
| L2 真实资金 | 真实支付、C 端条件退真金闭环 | `real_pay`，默认不在无人值守 CI 跑 |
| 人工兜底 | 短信通知、人机验证、破坏性退出登录 | 930 中人工/契约项 |

后续可以新增 marker：

```python
pytest.mark.release_core
pytest.mark.release_smoke
pytest.mark.release_money
pytest.mark.release_manual
pytest.mark.case_id("TC-005")
```

## 7. 下一步行动

建议按这个顺序推进：

1. 给现有自动化补 `case_id` 与 `release_core` 映射，不改变测试逻辑。
2. 生成一份机器可读的覆盖表，例如 `用例自动化映射.csv`。
3. 从 2000+ 人工用例中先导入 P0/P1，补齐 `模块/优先级/执行方式/是否上线必跑`。
4. 对齐人工用例与当前自动化，得到“已覆盖/半自动/未覆盖”三张清单。
5. 优先补 `release_core` 中未覆盖、且数据可控/断言明确的缺口。
6. 最后再改 `run.sh` 和 CI，增加 `./run.sh release` 入口。
